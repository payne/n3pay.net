# Claude Session: LXMF QR Code Encode/Decode

This documents the Claude Code session that produced `lxmf_qr.py` and `qr_lxmf.py`
in this directory.

## Goal

Demonstrate the LXMF "paper message" feature mentioned in `reticulum.md`: LXMF can
represent a fully signed, encrypted message as a QR code, meant to be printed or
scanned rather than transmitted over the network.

Two scripts were built:

1. `lxmf_qr.py` — reads a text file, packs its contents into an LXMF message, and
   saves a QR code of it as a PNG.
2. `qr_lxmf.py` — reads that PNG back, decodes and decrypts the QR code, and writes
   the recovered text to a file.

## Dependencies installed into `venv`

The venv already had `rns` (Reticulum) installed. Added:

```
venv/bin/pip install lxmf qrcode[pil] pillow
venv/bin/pip install opencv-python-headless
```

- `lxmf` — the LXMF protocol library (`LXMessage`, `LXMRouter`, etc.)
- `qrcode[pil]` / `pillow` — used internally by `LXMessage.as_qr()` to render the QR PNG
- `opencv-python-headless` — used by `qr_lxmf.py` (`cv2.QRCodeDetector`) to read a QR
  code back out of a PNG image, without needing a system `zbar` library

## `lxmf_qr.py` — text file → QR PNG

```
venv/bin/python lxmf_qr.py <input_text_file> [output_png_file]
```

Defaults the output path to the input filename with a `.png` extension.

Key design points:

- Builds an `LXMF.LXMessage` with `desired_method=LXMF.LXMessage.PAPER`, which is
  LXMF's built-in representation for a message meant to be encoded as a `lxm://...`
  URI and turned into a QR code, rather than delivered over the network.
- An LXMF message always needs a source and destination `RNS.Identity`/
  `RNS.Destination`, even for a paper message, since the message is still signed by
  the source and encrypted to the destination's public key.
- **Identities are persisted**, not generated fresh each run. They're stored in
  `.lxmf_identities/source_identity` and `.lxmf_identities/destination_identity`
  next to the scripts (created on first run via `RNS.Identity.to_file()`, loaded on
  later runs via `RNS.Identity.from_file()`).
  - This matters because the message content is encrypted to the destination
    identity's public key. If that identity were thrown away after the script
    exited (as an earlier draft did), the resulting QR code would be permanently
    undecryptable — there'd be no private key left anywhere that could open it.
- The QR image itself comes straight from LXMF's own `message.as_qr()` method,
  which internally calls `qrcode.make(...)` and returns a Pillow image.
- LXMF paper messages have a hard capacity limit (`LXMessage.PAPER_MDU`, roughly
  2.2KB of content after protocol overhead, since it all has to fit inside a single
  QR code). If the input file is too large, `as_qr()` raises `TypeError`, which the
  script catches and reports instead of crashing.

## `qr_lxmf.py` — QR PNG → text file

```
venv/bin/python qr_lxmf.py <input_png_file> [output_text_file]
```

Defaults the output path to the input filename with a `.txt` extension.

Key design points:

- Uses `cv2.QRCodeDetector().detectAndDecode(image)` to read the raw `lxm://...`
  URI string out of the PNG.
- Reimplements the inverse of `LXMessage.as_uri()`: strips the `lxm://` scheme,
  restores the base64 padding that was stripped when the URI was built, and
  base64-decodes it back into `paper_packed` bytes (`destination_hash +
  encrypted_data`).
- Loads `.lxmf_identities/destination_identity` (written by `lxmf_qr.py`) and
  builds an `RNS.Destination` from it in the `IN` direction, which is required to
  call `.decrypt()` (a destination built with a public-only identity can only
  `.encrypt()`, not `.decrypt()`).
- Verifies the loaded identity's destination hash actually matches the
  `destination_hash` embedded in the QR data before attempting decryption, and
  fails with a clear message if it doesn't (e.g. wrong identity file, or a QR code
  from a different source).
- Calls `RNS.Destination.decrypt()` to recover the original signed, packed LXMF
  payload, prepends the destination hash back on, and passes the result to
  `LXMF.LXMessage.unpack_from_bytes()` — the exact same code path LXMF's own router
  uses internally when delivering a real message — to get back an `LXMessage` with
  `.content_as_string()` holding the original text.

This mirrors the internals of `LXMRouter.lxmf_propagation()` /
`LXMRouter.lxmf_delivery()` in the installed `lxmf` package (see
`venv/lib/python3.11/site-packages/LXMF/LXMRouter.py`), which was read during this
session to confirm the correct decrypt-then-unpack sequence.

# Claude Session: Embedding Python Files in `reticulum.md` with Line Numbers

This documents a second Claude Code session, which added a way to display the
contents of `server.py` and `client.py` directly inside `reticulum.md`, with line
numbers, without adding any client-side JavaScript to the site.

## Goal

`reticulum.md` referenced "these two python programs" (the RNS hello-world
demo) but didn't actually show their contents. The ask was to display the
`.py` files in the post, preferring a rendering with line numbers.

## Constraints from the project

- The site is an Eleventy v3 blog (`eleventy.config.js`, `_includes/layouts/`)
  that intentionally ships zero client-side JavaScript.
- Syntax highlighting already goes through `@11ty/eleventy-plugin-syntaxhighlight`
  (Prism under the hood), with the Okaidia theme and a diff CSS file included
  per-post in `_includes/layouts/post.njk` via `<style>{% include "..." %}</style>`.
- Markdown files are pre-processed as Nunjucks (`markdownTemplateEngine: "njk"`),
  so custom Nunjucks shortcodes can be used directly inside `.md` files, and
  markdown-it is configured with `html: true`, so raw HTML blocks a shortcode
  returns pass through untouched.

## Why not just use `{% highlight %}`

The official syntax-highlight plugin's paired shortcode takes inline code as
its *content*, not a file path, and has no built-in line-number gutter — its
`highlightNumbers` option is for marking/emphasizing specific lines, not for
displaying a running line count. Prism's real line-numbers feature ships as a
separate plugin (`prismjs/plugins/line-numbers/`) that is normally applied by
a small runtime JS hook, which conflicts with the site's zero-JS goal.

## How it works

Prism's line-numbers plugin, read directly from
`node_modules/prismjs/plugins/line-numbers/prism-line-numbers.js`, turns out to
be pure CSS counters underneath: at runtime it just appends one empty
`<span>` per source line into a `<span class="line-numbers-rows">` container
inside `<code>`, and `prism-line-numbers.css` numbers them via
`counter-increment`/`::before { content: counter(linenumber) }`. Nothing about
that requires a browser — the exact same markup can be generated once at
build time, since the line count of a file is already known then.

Added to `eleventy.config.js`:

- Imports `prismjs` and `prismjs/components/prism-python.js` directly (import
  order matters: `prismjs/prism.js` sets a `global.Prism` that the untyped
  component file mutates, so the core import must run first).
- A `content/**/*.py` watch target, so the dev server rebuilds the post when a
  referenced `.py` file changes.
- A new `codeFile` universal shortcode:
  - Resolves the given filename relative to the *current page's* directory
    via `this.page.inputPath` (works because `addShortcode` is called with a
    plain `function`, not an arrow function, so Eleventy binds `this` to the
    page context).
  - Reads the file, strips one trailing newline, and runs it through
    `Prism.highlight(...)`.
  - Counts lines and builds the matching number of `<span></span>` line-number
    rows, producing the same markup shape the real Prism plugin builds at
    runtime:
    `<pre class="line-numbers language-python" data-src="..."><code class="language-python">{highlighted}<span aria-hidden="true" class="line-numbers-rows">{spans}</span></code></pre>`
  - Eleventy's Nunjucks engine automatically wraps shortcode return values in
    `nunjucks.runtime.SafeString`, so the raw HTML isn't escaped when used
    inside the markdown/njk post.

Added to `_includes/layouts/post.njk`:

- `<style>{% include "node_modules/prismjs/plugins/line-numbers/prism-line-numbers.css" %}</style>`,
  matching the existing pattern used for the Okaidia theme and diff CSS —
  scoped to blog posts only, bundled per-page like the rest of the site's CSS.

Added to `reticulum.md`:

- `{% codeFile "server.py" %}` and `{% codeFile "client.py" %}`, replacing the
  previously-empty reference to "these two python programs."

## Verified

- `npx @11ty/eleventy` build succeeded and produced the expected
  `<pre class="line-numbers language-python" data-src="server.py">...` /
  `data-src="client.py">...` markup with one `<span></span>` per source line
  in `_site/blog/Reticulum/reticulum/index.html`.
- Ran the Eleventy dev server locally and took a headless-Chromium screenshot
  (`chromium --headless --disable-gpu --no-sandbox --screenshot=... "http://localhost:8099/blog/Reticulum/reticulum/"`)
  to visually confirm the numbered gutter, syntax colors, and dark theme
  render correctly — matching the rest of the site's styling.
